# Подключение подписанного учёта к FUP

Реализация: `ElX-control` — единственный владелец подписанных учётных потоков, их журналов, миграций и расписаний.

Назначение подписанного потока — привилегированная операция администратора Control. На сервере уже должны существовать entitlement, действующее FUP-расписание, rate grant на нужной ноде и закреплённый публичный ключ текущего ElXray.

Команда `elx-control provision-usage` принимает аргументы `-entitlement`, `-schedule`, `-node`, `-resource`, `-executor`, `-incarnation`, `-accounting`, `-generation` и `-subscription`. Указанный subscription ID должен быть предварительно подтверждён оператором по доверенной привязке политики; текущая реализация не доказывает его соответствие rate resource автоматически.

Команда возвращает объект `Binding`, который устанавливается в защищённый файл ноды `ELX_USAGE_BINDINGS`. На ноде запускается `elx-control serve-usage -interval 5s` через доверенное mTLS-подключение и локальный API ElXray. В Control команда `elx-control usage-coverage -entitlement UUID -schedule UUID` сообщает, сколько grant имеют назначения и исходные подписанные замеры.

Миграция 013 сохраняет точную привязку ресурса и добавляет `primed` для накопительных счётчиков: первое измерение фиксирует базовую точку без начисления старого трафика. После первого подтверждения учитывается только последующая разница. Календарный rollover переносит привязку и watermark.

`ready=true` означает, что все активные grant назначены и для них принимались свежие подписанные показания за последние 30 секунд. Повтор старого подписанного сообщения не продлевает свежесть. `freshGrants` отдельно показывает количество таких источников; `primedGrants` — сколько хотя бы один раз приняли исходный замер. Это не гарантия свежести текущих показаний, корректного исполнения ограничений в ядре или достаточной защиты при сетевых разделениях. До коммерческого применения потребуются контроль свежести потоков, подтверждение subscription-to-resource и безопасная ротация ядра/назначений.

Миграция `014_usage_freshness.sql` добавляет время последнего принятого нового sequence. Календарный rollover сохраняет последнее значение, но не делает устаревший поток свежим автоматически.
