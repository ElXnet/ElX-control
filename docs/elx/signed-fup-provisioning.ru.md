# Подключение подписанного учёта к FUP

## Автоматическое назначение через доверенный манифест

Для новых узлов и подписок используйте `auto-provision-usage` вместо ручного ввода `subscription`, `resource`, `incarnation`, `executor` и `accounting`:

```bash
# Запускается только доверенным оператором Control с правами на PostgreSQL.
# ELX_POLICY_BINDING — тот же закрытый JSON-манифест, который использует serve-policy.
./elx-control auto-provision-usage -entitlement UUID -schedule UUID
```

Control сопоставляет каждый оплаченный rate grant указанного entitlement с записью этого же манифеста по `node_id + resource_id`, проверяет эпоху и публичный ключ границы скорости, затем находит **единственный** неотозванный экземпляр ядра с тем же ключом. Все активные grants должны присутствовать в манифесте, иначе операция отменяется до первого назначения. `executor_id` и `accounting_id` формируются детерминированно и повторный вызов возвращает уже созданные привязки.

Подписанный учёт ноды по умолчанию получает актуальный перечень своих назначений через метод `SignedAccounting/Bindings`, защищённый mTLS, при каждом цикле `serve-usage`. Отдельный файл `ELX_USAGE_BINDINGS` больше не нужен; его можно оставить как явно включаемый совместимый режим для локальных тестов. Сервер не раскрывает ноде подписки других нод и не принимает от неё произвольные назначения. При недоступности Control агент не использует устаревший список.

Режим автоматизации не создаёт профиль Xray из платёжного уведомления и не является готовым billing-провижинингом. Он безопасно связывает **уже выданный** оплаченный rate grant с подпиской, закреплённой в операторском манифесте. При несовпадении ключей, нескольких неотозванных экземплярах ElXray или смене подписки операция завершается отказом. Ротация старого экземпляра остаётся отдельной транзакционной процедурой: автоматически переиспользовать прежний учётный поток нельзя.


Реализация: `ElX-control` — единственный владелец подписанных учётных потоков, их журналов, миграций и расписаний.

Назначение подписанного потока — привилегированная операция администратора Control. На сервере уже должны существовать entitlement, действующее FUP-расписание, rate grant на нужной ноде и закреплённый публичный ключ текущего ElXray.

Команда `elx-control provision-usage` принимает аргументы `-entitlement`, `-schedule`, `-node`, `-resource`, `-executor`, `-incarnation`, `-accounting`, `-generation` и `-subscription`. Указанный subscription ID должен быть предварительно подтверждён оператором по доверенной привязке политики; текущая реализация не доказывает его соответствие rate resource автоматически.

Команда возвращает объект `Binding`, который устанавливается в защищённый файл ноды `ELX_USAGE_BINDINGS`. На ноде запускается `elx-control serve-usage -interval 5s` через доверенное mTLS-подключение и локальный API ElXray. В Control команда `elx-control usage-coverage -entitlement UUID -schedule UUID` сообщает, сколько grant имеют назначения и исходные подписанные замеры.

Миграция 013 сохраняет точную привязку ресурса и добавляет `primed` для накопительных счётчиков: первое измерение фиксирует базовую точку без начисления старого трафика. После первого подтверждения учитывается только последующая разница. Календарный rollover переносит привязку и watermark.

`ready=true` означает, что все активные grant назначены и для них принимались свежие подписанные показания за последние 30 секунд. Повтор старого подписанного сообщения не продлевает свежесть. `freshGrants` отдельно показывает количество таких источников; `primedGrants` — сколько хотя бы один раз приняли исходный замер. Это не гарантия свежести текущих показаний, корректного исполнения ограничений в ядре или достаточной защиты при сетевых разделениях. До коммерческого применения остаются необходимые проверки исправности агента на узле, безопасная ротация ядра/назначений и автоматическая выдача профиля после оплаты.

Миграция `014_usage_freshness.sql` добавляет время последнего принятого нового sequence. Календарный rollover сохраняет последнее значение, но не делает устаревший поток свежим автоматически.

## Безопасная активация правила

Новое расписание после регистрации в личном кабинете или административном API создаётся с `enabled=false`. Оно не уменьшает лимит скорости и не препятствует выдаче lease, пока нет подписанного учёта.

Оператор сперва назначает все необходимые потоки `auto-provision-usage` (для совместимости доступен ручной `provision-usage`), включает на каждой ноде `serve-usage` и проверяет, что `usage-coverage` сообщает `ready=true`. После этого команда `elx-control activate-fup -entitlement UUID -schedule UUID` атомарно включает расписание. При недостающем или устаревшем подписанном источнике активация отклоняется. Пользовательское создание правила не предоставляет права на его немедленную активацию.

После активации новая подпись 15-секундного Control lease выдаётся только при наличии свежих подписанных показаний по всем положительным скоростным назначениям. При потере или отзыве источника разрешение перестаёт продлеваться; если обязательный lease включён на ElXray и агенте, ядро прекращает пропускать трафик после истечения последнего разрешения. В режиме без обязательного lease такая защита от обрыва связи не действует.

Расписание в ожидании активации продолжает сменять календарные периоды и переносить watermark подписанного источника. События порога из него не меняют реальный бюджет до активации.
