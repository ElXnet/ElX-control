# ElX — финальный приёмочный прогон технического этапа (Control / ElXray / ElX-ui)

Актуально для разработческой ветки `test/p0-fup-scheduler-interleaving-20261107`.
Три компонента независимы: исходники и PostgreSQL-схема Control не
переносятся в панель. Перечисленные ниже сценарии относятся к серверной
инфраструктуре; приложение, Telegram, Caddy, WebRTC и детальный UX ЛК сюда
**не входят**. Итоговый статус определяется **результатом полного запуска**,
а не наличием тестового файла или зелёным статусом отдельного PR.

## Автоматизированные критические гейты

| Область | Проверка | В автоматическом наборе |
| --- | --- | --- |
| Policy / data plane | Две настоящие локальные VLESS-ноды, mTLS Control, подписанные политики и counters | `tests/e2e/test_multinode.py` |
| Общая полоса | Одновременно upload/download; не превышать заданные две нодовые квоты | `tests/e2e/test_rate_partition.py` |
| 15-секундные разрешения | Отказ Control закрывает старые соединения и запрещает новые; после восстановления разрешены только новые | `tests/e2e/test_lease_partition.py` |
| Автоматическое распределение | Подписанные давление лимитера и принятый lease, снижение idle-ноды, отдельный подписанный rate barrier, повышение busy-ноды | `tests/e2e/test_live_scheduler.py` |
| Конфликт FUP и scheduler | Изменение лимита во время pending reduction, запрет stale raise, ожидание signed barrier, идемпотентный reconcile | `internal/elxcontrol/journal/fup_scheduler_interleaving_postgres_test.go` |
| Реальный FUP + авария | Превышение порога подписанным VLESS-трафиком, отказ Control, истечение lease, восстановление лимитов и смена leader epoch | `tests/e2e/test_live_fup_scheduler.py` |
| Слоты и подписи | Конкурентные устройства, запрет лишних слотов, подписанный drain и защита от чужого ключа | `internal/elxcontrol/journal/two_device_slots_postgres_test.go` |
| Конкурентность на 200 | 200 уникальных device-proof резервирований на 3 нодах + 10 отказов при исчерпании слотов | `internal/elxcontrol/journal/session_scale_postgres_test.go` |
| ElXray | VLESS, Vision TLS/REALITY, UDP/XUDP/Mux, ограничение скорости, подписанные proof; тесты Go по всем пакетам | `scripts/elxray-full-go-tests.sh`, `testing/subscriptionrate` |
| ElX-ui | PostgreSQL миграции, API scope/CSRF, Unix-socket proxy, frontend, node-E2E и vulncheck | `scripts/elx-test-all.sh` |

Все локальные E2E используют loopback / одноразовый PostgreSQL. Никакие
локальные результаты не равнозначны реальной доступности VPS или клиента.

## Единственный полный запуск на Windows/WSL

**Дождитесь слияния PR**, после чего переключите все три рабочих
репозитория на чистый `main`. В PowerShell:

```powershell
git -C D:\ElX-test\ElX-control switch main
git -C D:\ElX-test\ElXray switch main
git -C D:\ElX-test\ElX-ui switch main
powershell -ExecutionPolicy Bypass -File D:\ElX-test\ElX-control\scripts\run-elx-windows.ps1 -Workspace D:\ElX-test -Distro Ubuntu -Full
```

Скрипт проверяет отсутствие незакоммиченных изменений, обновляет `main`
для всех трёх репозиториев, фиксирует три точные SHA и сохраняет лог
`D:\ElX-test\test-logs\ElX-full-*.txt`. Если любая проверка падает,
полный прогон считается **FAIL** независимо от числа прошедших сценариев.

Для быстрого повтора **после исправления** можно запустить обычный
интеграционный режим без `-Full`, но для закрытия этапа необходим `-Full`.

## Границы результатов и обязательные внешние проверки

1. **Физическая device identity пока не доказана:** серверный
   Ed25519 proof и 200 записей в БД не запрещают второй физической
   машине пользоваться копией одного стандартного VLESS-ключа. Проверка
   привязки реального handshake к устройству требует согласованного
   изменения протокола/клиента и теста с двумя ПК. Пока не подтверждено,
   нельзя обещать аппаратное ограничение устройств.
2. **TUN**: локальные loopback-тесты не создают системный TUN. Реальный
   Windows TUN, DNS, IPv6, MTU, UDP/QUIC, kill switch и смена сети
   проверяются на отдельных устройствах после интеграции клиента.
3. **Полноценный HA PostgreSQL**: две параллельные Control-scheduler
   реплики и новый leader epoch в общей PostgreSQL проверяются, но
   настоящий split-brain, смена primary и сетевые разделения
   PostgreSQL кластера не моделируются в этом однохостовом стенде.
4. **Реальные 200 VPN-клиентов** и длительный soak на хостинге не
   эквивалентны 200 криптографическим резервациям слотов в тестовой БД.
5. **Биллинг, интеграция Telegram и внешний жизненный цикл оплаты** —
   отдельный этап. Ключ подписки не должен давать права управления.
6. **Автоматический scheduler** включается только при явной переменной
   `ELX_RATE_SCHEDULER_ENABLED=1`; даже успешный `-Full` сам по себе
   не является разрешением включать его для платящих пользователей без
   оценки внешних критериев выше.

## Если прогон не прошёл

Прикрепите **полный лог**, а не только последние строки. Для каждого
падения важны точные SHA всех репозиториев, `FAIL`/panic/traceback,
вывод тестового PostgreSQL и итоговый EXIT CODE. Перед передачей
за пределы доверенной команды проверьте отсутствие секретов, токенов
и реальных адресов.
