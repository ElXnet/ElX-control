# Сквозная проверка применения политики ElX

## Автоматическая очередь закрытия активного устройства

Для закрытия VPN-сессии Control использует отдельную, идемпотентную
операцию над уже занятым слотом — `session.QueueDrain`. На тестовом
мастер-узле администратор может вручную поставить её командой:

```bash
# Только из доверенного административного контекста Control.
# Клиентская подписка и доступ к API узла НЕ являются авторизацией.
./elx-control enqueue-drain -owner UUID_ЗАНЯТОГО_СЛОТА
```

Задача переводит запись `elx_session_owners` в состояние `draining`,
не освобождая слот. Рабочий `serve-agent` теперь выполняет два
независимых действия при каждом опросе: получение политики и
`SessionFence/Next`. Вторая RPC возвращает только разрешённую Control
задачу для **его mTLS-идентичности ноды**. Агент просит локальный ElXray
закрыть аутентифицированный VLESS UUID, получает подписанное
`SessionFence v2` и отправляет его через `SessionFence/Submit`.

Control разрешает состояние `released` **только** если слот
предварительно был помечен `draining`, а подпись соответствует
зарегистрированному ключу ядра, `ProfileID`, `OwnerID`,
`Generation`, `NodeID` и `Incarnation`. Потеря ACK безопасна:
запрет остаётся на диске ElXray, запрос остаётся в журнале Control и
следующий опрос повторяет операцию. Подписи по чужому профилю, старой
генерации или без запроса на закрытие отвергаются.

**Для личного кабинета** нужно вызывать `session.QueueDrain` через
авторизованный backend после проверки владельца подписки. Не публикуйте
команду `enqueue-drain` как анонимный HTTP endpoint. Запрос пользователя
«отключить устройство» — это начало операции; подтверждение её
завершения происходит только после проверенного сообщения от ядра.
Если сервер упал до выдачи подписи и ядро перезапустилось с новой
`Incarnation`, старый слот остаётся занятым до отдельной процедуры
reconciliation. Истечение TTL само по себе его не освобождает.

## Реальное закрытие VLESS-профиля из ElXray

В рабочей ветке `ElXray/restrict-runtime-unlimited` добавлен локальный RPC
`/xray.app.policy.command.ProfileFence/Drain`. В отличие от простого
отключения подписки, он удерживает **запрет нового входа только для
аутентифицированного VLESS UUID** и дожидается завершения всех потоков этого
профиля, включая соединения с Mux. Запрет сохраняется в
`ELXRAY_POLICY_STATE` и переживает перезапуск ядра. Пока отказ базы,
отсутствие профиля, несовпадение incarnation или открытый поток не
устранены — ядро не выдаёт подпись.

**Контракт идентичности:** `ProfileID` в записи активного слота Control
должен быть равен настоящему VLESS UUID, который проходит проверку при
рукопожатии. Никогда не подменяйте его email, IP-адресом клиента,
произвольным device-ID или HWID. Старые слоты, для которых нельзя доказать
эту привязку, остаются занятыми.

На **доверенном supervisor рабочей ноды** с локальным Unix-socket ElXray и
привязанным через `ELX_POLICY_BINDING` публичным ключом можно выполнить:

```bash
# Требуется настроенный mTLS, локальный ElXray Commander и доверенный
# ELX_POLICY_BINDING; учетные записи/UUID сначала выдаёт Control.
./elx-control drain-profile \
  -owner UUID_ЗАНЯТОГО_СЛОТА \
  -profile UUID_VLESS_АККАУНТА \
  -node UUID_НОДЫ \
  -incarnation UUID_ЗАПУСКА_ЯДРА \
  -generation 1
```

Команда дожидается подписанного `SessionFence v2`, проверяет Ed25519
подпись локально и передаёт доказательство на
`elx.node.v1.SessionFence/Submit` через mTLS. Сервер Control
сверяет профиль, поколение, ноду, incarnation и ключ в транзакции перед
освобождением слота. После потерянного ACK можно **повторить те же
аргументы**: ядро повторно подтверждает уже закрытый профиль.

Подпись и долговременный запрет работают на **Linux**, где реализована
защита файлового журнала `ELXRAY_POLICY_STATE`. Для тестов на Windows
используйте WSL Ubuntu / Docker Linux: нативный Windows-бинарник ядра не
должен выдавать `SessionFence` без надёжного сохранения запрета.
Повторная активация того же VLESS UUID после подтверждённого drain
**не допускается автоматически**. Control должен выдать новый, отдельно
привязанный VLESS-профиль и новую генерацию владения слотом.

Это путь для защищённого supervisor, а **не** функция клиентской подписки.
Автоматическая постановка команды закрытия при запросе через личный
кабинет и подтверждение её выполнения требуют отдельного связывания
с контроллером жизненного цикла устройств. Нельзя выдавать доступ к
локальному Commander обычному пользователю или рассчитывать, что
таймаут сам по себе освобождает активный слот.

## Удалённый сбор подписанного трафика (mTLS)

Теперь транспорт `elx.node.v1.SignedAccounting` регистрируется на **том же защищённом gRPC-сервере**, что `serve-policy`. Узел работает только с локальным API ElXray и mTLS-клиентским сертификатом. Удалённой ноде **не требуется DSN PostgreSQL**.

До запуска Control должен доверенно зарегистрировать запись `elx_core_identities`, текущий `elx_period_schedules`, `elx_accounting_streams`, `elx_accounting_assignments` и `elx_rate_budgets`. Нода не может создать себе эти назначения. В конфигурационном файле узла `/etc/elx/usage-bindings.json` указываются только UUID уже существующей привязки:

```json
[
  {
    "NodeID": "UUID_НОДЫ",
    "ExecutorID": "UUID_ИСПОЛНИТЕЛЯ",
    "Incarnation": "UUID_ЗАПУСКА_ELXRAY",
    "AccountingID": "UUID_ПОТОКА_УЧЁТА",
    "Generation": 1,
    "ScheduleID": "UUID_РАСПИСАНИЯ_FUP"
  }
]
```

Команды для **Linux / WSL**, при установленном бинарнике `elx-control`:

```bash
export ELX_POLICY_CONTROL="control.example:443"
export ELX_TLS_CERT="/etc/elx/node.crt"
export ELX_TLS_KEY="/etc/elx/node.key"
export ELX_TLS_CA="/etc/elx/node-ca.crt"
export ELXRAY_POLICY_SOCKET="/run/elxray/policy.sock"
export ELX_USAGE_BINDINGS="/etc/elx/usage-bindings.json"

# Одна подписанная выборка и результат её приёма Control
./elx-control serve-usage -once

# Непрерывный сбор каждые 5 секунд
./elx-control serve-usage -interval 5s
```

Путь к локальному API ElXray должен быть доступен только доверенному supervisor. Не передавайте клиенту секреты nodelink, mTLS или PostgreSQL. Control генерирует одноразовый 128-битный nonce, ядро подписывает ответ Ed25519, Control проверяет его закреплённым публичным ключом и в одной транзакции погашает challenge и записывает прирост трафика. Потерянный ACK обрабатывается новым challenge и накопительным счётчиком: повторно начислять байты нельзя.

### Важные ограничения

- Тесты проверяют реальный TLS 1.3, отклонение чужого узла, подмены ключа и повторного evidence, а также PostgreSQL-учёт двух нод. Это не нагрузочное испытание на двух физических компьютерах.
- При отсутствии связи Control **не знает фактический текущий расход трафика удалённой ноды**. Поэтому пока в самом ElXray нет истекающих локальных lease/политик, нельзя обещать мгновенное глобальное соблюдение нового FUP при сетевом разделении.
- Подтверждение завершения сессии передаётся через `elx.node.v1.SessionFence` только при наличии подписанного ядром proof. Схема версии 2 связывает `OwnerID + ProfileID + Generation + NodeID + Incarnation`. **ElXray ещё не формирует этот receipt после реального запрета новых VLESS-потоков и полного drain**, поэтому этот путь нельзя считать готовым освобождением занятого слота.
- Миграция `011_session_profile_binding.sql` оставляет существующие записи с неизвестным `ProfileID` занятыми до достоверного восстановления; не освобождайте их принудительно по таймеру.

Скрипт клонирует или безопасно обновляет три рабочие ветки, откажется работать при незакоммиченных изменениях и запустит полную локальную проверку из `ElX-control` через WSL. В этой проверке используется реализация Control из самостоятельного репозитория. При неудаче сохраните текст консоли и путь с тестовыми логами, напечатанный скриптом. Секреты/DSN не присылайте.

## Подписанные подтверждения закрытия сессии

Миграция `007_core_identities.sql` вводит доверенную привязку `(node_id, incarnation) → Ed25519 public_key`. Перед разрешением переноса занятого слота оператор управляющего контура должен зарегистрировать ключ, полученный по **проверенному** каналу идентификации конкретного ElXray. Ключ из тела клиентского запроса, сообщения о закрытии или произвольного сертификата без сверки привязки не подходит.

`session.ReleaseAfterFence` отклоняет незарегистрированные, отозванные и несовпадающие ключи, даже если предъявленная подпись сама по себе корректна. Старые слоты остаются занятыми до достоверного подтверждения закрытия, при потере связи применяется fail-closed. Оперативная автоматическая регистрация, ротация и подпись самого fence на уровне ElXray ещё требуют интеграции; нельзя считать имеющуюся проверку полноценным end-to-end завершением сессии.


## Автоматическая доставка политик и FUP

В Control предусмотрены два независимых фоновых процесса (оба запускаются с действующими служебными правами, а не от имени клиента):

```bash
# Master / Control: каждые 5 секунд ищет активные события FUP
export ELX_CONTROL_POSTGRES_DSN='...тестовый или защищённый production DSN...'
./elx-control serve-fup -interval 5s

# Рабочая VPN-нода: по mTLS получает pending-операции, применяет
# их к локальному ElXray и отправляет подписанное подтверждение
export ELX_POLICY_CONTROL='control.example:443'
export ELX_TLS_CERT='/etc/elx/node.crt'
export ELX_TLS_KEY='/etc/elx/node.key'
export ELX_TLS_CA='/etc/elx/node-ca.crt'
export ELXRAY_POLICY_SOCKET='/run/elxray/policy.sock'
./elx-control serve-agent -interval 2s
```

Для разового прогона вместо `serve-fup` можно вызвать `reconcile-fup`. Он не поднимает слушатель и не требует ключей ноды. Внешний управляющий процесс должен предварительно создать `elx_rate_budgets`, `elx_rate_grants` и привязки нод, а также запускать `serve-policy`. Временная потеря связи не удаляет операцию из журнала; агент повторяет её после восстановления канала.

FUP планирует **только снижения** и не увеличивает скорость автоматически после завершения периода. Приоритетом остаётся безопасность: `elx_rate_grants.committed_*` не уменьшается до подписанного барьера безопасного снижения скорости. Пока протокол такого барьера не связан с ElXray, Control сохраняет старые резервирования и не может перераспределить высвобожденные скорости на другие ноды. Расчёт снижения для двух нод и конкурирующих согласователей покрыт PostgreSQL-тестами. Приведённый способ не является готовой коммерческой эксплуатацией или гарантией отсутствия кратковременных превышений при переходе FUP.

## Календарное завершение периода FUP

`serve-fup` без `-entitlement` также вызывает `journal.AdvanceDue` перед каждым пересчётом. Для ручной однократной проверки предусмотрено:

```bash
./elx-control advance-periods
```

Расписания создаются только доверенным управляющим контуром в таблице `elx_period_schedules`: `cadence=day|week|month`, `timezone_name` — зона IANA (например, `Europe/Moscow`), `current_period_id` — уже созданный `elx_usage_periods`. Для месячного периода граница должна приходиться на **первое число в 00:00** локального времени, для недельного — на **понедельник в 00:00**, для суточного — на локальную полночь. После создания расписания связанный `elx_usage_periods.schedule_id` должен содержать ID расписания. Это операции provisioning, не поля клиентской подписки.

При переходе `AdvancePeriod` в одной транзакции закрывает старые `elx_accounting_streams`, переносит их sequence и накопительные байты в новый период, копирует доверенные назначения `elx_accounting_assignments` и обновляет `current_period_id`. Поэтому новый период учитывает **приращение**, а не весь накопленный трафик ElXray повторно. Если между последним опросом ядра и моментом календарной границы был трафик, он будет отнесён к новому периоду при первом чтении — точное разнесение по секундам невозможно без отдельного потока событий. Это ограничение важно для отчётности и возможного биллинга.

Новая локальная команда `collect-current` определяет актуальный период внутри транзакции и блокирует переход периода до завершения подписанного readback:

```bash
./elx-control collect-current -node UUID_NODE -executor UUID_EXECUTOR \
  -incarnation UUID_CORE_BOOT -accounting UUID_STREAM \
  -generation 1 -schedule UUID_FUP_SCHEDULE
```

В отличие от `collect-usage`, здесь **нет** аргумента `-period`: его выбирает доверенная БД. При rollover запись с прежним периодом отклоняется, а новое значение выбирается в следующем вызове. Для локального лабораторного стенда используется защищённый сокет ElXray и доверенный PostgreSQL. Это **не** разрешение выдавать произвольным нодам прямой доступ к БД Control. Удалённая передача подписанного usage evidence через mTLS, регулярный опрос удалённых нод и защита от длительно отсутствующих показаний ещё требуют отдельного контура, поэтому полностью автоматический end-to-end FUP на произвольной VPN-нode пока не заявляем.

## Один запуск из WSL

В Linux или WSL установите Go версии из `go.mod`, C-компилятор для `-race`, OpenSSL и Python 3. Если своей тестовой БД нет, запустите Docker Desktop с интеграцией WSL. В каталоге для тестов выполните:

```bash
git clone --branch restrict-runtime-unlimited https://github.com/ElXnet/ElXray.git
git clone --branch feat/multinode-policy https://github.com/ElXnet/ElX-control.git
cd ElX-control
set -o pipefail
bash scripts/elx-test-local.sh 2>&1 | tee elx-test.log
```

Если репозитории уже скачаны, обновите указанные ветки через `git pull --ff-only`. Сценарий печатает коммиты, собирает оба бинарника, запускает Go-тесты с PostgreSQL и `-race`, проверяет доставку на две ноды и отключение открытого VLESS/TCP-соединения. На успехе выводит `PASS: ElX local suite`. При сбое приложите `elx-test.log`.

По умолчанию сценарий поднимает временный контейнер PostgreSQL и удаляет его после прогона. Для существующей **тестовой** базы задайте `ELX_CONTROL_POSTGRES_DSN`. Для ElXray из другого каталога задайте `ELXRAY_SOURCE`. Сквозная проверка VLESS использует локальный echo-сервер. Она проверяет отключение подписки целиком. Проверки идентификации устройства в реальном VPN-потоке и передачи слота между нодами добавляются вместе с этим контуром.

## Ручной запуск проверки доставки

Стенд запускает два экземпляра ElXray с разными ключами и одной логической подпиской. Control доставляет политики каждому экземпляру независимо. Команда проходит через PostgreSQL, gRPC с mTLS, ElXray и подписанное подтверждение. Команды нода забирает по одной через `apply-policy`. Ревизия ядра 1 соответствует ревизии журнала 0. Идентификатор операции сохраняется при повторной доставке.

Запускайте команды из Linux или WSL. Достаточно одного компьютера. Go и OpenSSL должны быть доступны внутри WSL, Docker Desktop должен быть подключён к этой WSL-дистрибуции. Скрипт применяет миграцию и оставляет записи в отдельной тестовой базе.

1. Возьмите ветку `feat/multinode-policy` в ElX-control и `restrict-runtime-unlimited` в ElXray. В примере репозитории лежат рядом.
2. Соберите бинарники. Версию Go берите из `go.mod` ElX-control.

   ```bash
   cd ElXray
   go build -o ../elxray-lab ./main
   cd ../ElX-control
   go build -o ../elx-control-lab ./cmd/elx-control
   ```

3. Запустите отдельную тестовую базу и дождитесь готовности PostgreSQL.

   ```bash
   docker run -d --name elx-test-pg -p 127.0.0.1:55432:5432 \
     -e POSTGRES_USER=elx -e POSTGRES_PASSWORD=elx_test \
     -e POSTGRES_DB=elx_test postgres:18
   docker exec elx-test-pg pg_isready -U elx -d elx_test
   ```

4. Когда `pg_isready` покажет `accepting connections`, запустите тест.

   ```bash
   export ELX_CONTROL_POSTGRES_DSN='host=127.0.0.1 port=55432 user=elx dbname=elx_test password=elx_test sslmode=disable'
   export ELXRAY_BIN="$(realpath ../elxray-lab)"
   export ELX_CONTROL_BIN="$(realpath ../elx-control-lab)"
   bash scripts/elx-policy-smoke.sh
   ```

5. Ожидаемый вывод: `PASS: mTLS, two nodes, wrong-core rejection, durable restart and replay`. При сбое пришлите вывод скрипта и версии бинарников. Не присылайте ключи, сертификатные seed или DSN с паролем. Если порты заняты, задайте `ELX_SMOKE_CONTROL_PORT` `ELX_SMOKE_CORE_PORT` и `ELX_SMOKE_SECOND_PORT`. После проверки тестовый контейнер можно остановить командой `docker stop elx-test-pg`.

Скрипт создаёт временный каталог с закрытыми правами. В нём остаются конфигурация, ключи стенда и журналы. Каталог можно удалить после проверки.

В постоянном окружении настройте отдельный CA нод и выдайте каждой ноде клиентский сертификат с URI SAN `spiffe://elxnet/node/<uuid>`. Control читает список привязок из JSON-файла `ELX_POLICY_BINDING`. На одной ноде локальная подписка соответствует одному ресурсу журнала. Ноды используют разные публичные ключи ElXray. При нескольких привязках `enqueue-policy` требует `-node` и `-resource`. Приватный seed и манифест состояния принадлежат процессу ядра. Хранилище располагается на локальной файловой системе, а процесс запускается с `ELXRAY_POLICY_STATE`. Стенд использует TCP loopback. Для локального агента на хосте предусмотрен `ELXRAY_POLICY_SOCKET` с ограничением доступа правами ОС.

Подпись подтверждает сохранённую конфигурацию конкретной подписки и привязана к ноде, ресурсу, операции и эпохе. Она не подтверждает закрытие потоков, безопасное перераспределение бюджета или защиту от восстановления устаревшей копии диска. Для этих сценариев потребуются отдельные контракты и проверки. При смене привязки либо восстановлении снимка управляющий контур следует остановить до сверки состояния.
