# Оплаченный доступ и безопасная замена ElXray

## Граница сервиса оплаты

Проверка зачисления денег выполняется **в отдельном payment-verifier** (банк, QPlus или другой провайдер — деталь его собственной реализации). ElX Control **не входит в банк**, не хранит телефон/пароль/банковскую сессию и никогда не принимает подтверждение от браузера, Telegram-бота или ElX-ui. Платёжный сервис после фактического settlement формирует версионированное событие, подписывает его Ed25519 своим приватным ключом и доставляет только на специальный сокет Control.

```
ЛК /lk → POST /lk/v1/orders → pending order
   ↓ пользователь оплачивает через выбранного провайдера
payment-verifier (отдельный процесс, проверяет settlement)
   ↓ подписанное событие + повторная доставка до подтверждения
ELX_PAYMENT_SOCKET → POST /billing/v1/confirmed
   ↓ проверка pinned публичного ключа, суммы, валюты, заказа и повторов
Control PostgreSQL: receipt + 30-дневные права + VLESS-профиль + outbox
   ↓ отдельный ElX-ui worker
disabled profile → pin policy/readback + all-node reconcile → enable
```

Утверждённый тариф: **500 ₽ / 30 дней / 2 активных устройства**; +200 ₽ за каждое из не более двух дополнительных устройств. В базовом тарифе общий лимит отправки и получения — 100 Мбит/с в каждом направлении, распределяемый между нодами. Клиент не задаёт сумму, скорость или количество слотов напрямую. Повтор того же подписанного события не продлевает доступ второй раз; иной event/provider payment с тем же платежом или изменёнными параметрами отклоняется.

Доверие к платёжному событию основано на подписи, совпадении заказа/суммы, времени платежа и уникальности provider transaction. **Сам HTTP-запрос заказа не подтверждает оплату.** Payment-verifier обязан независимо сверять окончательный статус операции и аутентичность API провайдера; helper `billing.SignForVerifier` только формирует подписанный wire-контракт после такой проверки.

## Изоляция входа платёжного сервиса

Используются **разные** Unix-сокеты и процессы:

- `ELX_MANAGEMENT_SOCKET` — только master Control и доверенный ElX-ui. Здесь находятся управление, LK и `/provision/v1/{claim,ack}`. `/billing/v1/confirmed` больше не смонтирован.
- `ELX_PAYMENT_SOCKET` — процесс `elx-control serve-payment-ingress`, единственный маршрут `POST /billing/v1/confirmed`. Любой административный/провижининговый путь возвращает 404.

При развёртывании на одной Linux-машине создайте **отдельного системного пользователя** для payment-verifier и отдельную группу доступа только к платёжному сокету. Не добавляйте verifier в системную группу/UID Control. Каталоги сокетов должны быть защищены от записи посторонними, а `ELX_MANAGEMENT_SOCKET` остаётся режимом `0600`. Укажите `ELX_PAYMENT_GID` (числовой ID специальной группы) для режима `0660` только на сокете оплаты. Без переменной платежный сокет остаётся `0600` и доступен лишь владельцу.

```bash
# Оба процесса имеют настроенный ELX_CONTROL_POSTGRES_DSN.
# ELX_PAYMENT_VERIFY_KEY — файл с base64 Ed25519 PUBLIC key (не приватным).
ELX_PAYMENT_VERIFY_KEY=/etc/elx/payment-verifier.pub \
ELX_PAYMENT_SOCKET=/run/elx-payment/confirmed.sock \
ELX_PAYMENT_GID=1234 \
./elx-control serve-payment-ingress

# Отдельный процесс Control (НЕ делитесь его сокетом с payment-verifier).
ELX_MANAGEMENT_SOCKET=/run/elx-control/management.sock \
./elx-control serve-management
```

`1234` — пример, замените реальным GID выделенной Unix-группы. Каталог платёжного сокета должен быть доступен verifier для поиска файла (например, `0750` с корректным владельцем/группой) и недоступен остальным. Для verifier на отдельном хосте необходим отдельный защищённый транспорт до узкого payment-ingress; **не публикуйте Unix-менеджмент в TCP/Nginx без дополнительной аутентификации**.

## Выпуск оплаченного VLESS-профиля

1. Личный кабинет с cookie/CSRF создаёт `POST /lk/v1/orders`, получает рассчитанную Control сумму, и показывает `pending`. Только отдельный verifier может превратить его в `paid`.
2. Control в одной транзакции создаёт/продлевает entitlement, slots, общий rate budget, профиль с устойчивыми VLESS UUID, subscription ID и email, квитанцию и durable outbox. При повторе возвращается тот же профиль.
3. ElX-ui worker (`internal/web/job/elx_profile_job.go`) периодически забирает `/provision/v1/claim` по локальному Unix-сокету и сначала создаёт **отключённый** VLESS-клиент на всех доверенно выбранных `ELX_PROVISION_INBOUNDS`. Список должен охватывать мастер и необходимые remote-node inbound. Запросы не создают произвольные inbounds.
4. Только после подтверждения pinned policy, подписанного состояния ядра, оплаченных скоростных грантов и учёта FUP Control выдаёт `enable`. Worker требует совпадения UUID/SubID/email, прикрепления к каждому configured inbound, активного локального Xray и отсутствия отложенной конфигурации. Удалённые ноды должны быть `online` и не иметь `config_dirty`. Иначе ACK не отправляется; leased outbox повторяется с теми же данными.
5. ЛК получает subscription ID только после статуса профиля `active`. Этот bearer ID позволяет подключаться и диагностировать ошибки, но **не** даёт прав управлять устройствами/FUP. Управление требует входа в ЛК.

Активация при отсутствии любых необходимых grants, mandatory Control leases или подтверждённой доставки на ноду запрещена. Панельная синхронизация `config_dirty=false` свидетельствует о завершении своего reconciliation, **но не является независимым криптографическим доказательством наличия VLESS-пользователя в ядре**. Для коммерческой строгой гарантии нужно связывать ACK с отдельным подписанным readback профиля из ElXray; текущий activation gate подтверждает подписанную rate policy, а не каждый удалённый VLESS-user отдельно.

Отдельная обработка банковских API и кассовых/фискальных документов в этом репозитории **не реализуется**.

## Ротация живого экземпляра ElXray

Ротация защищает **занятые слоты**, а не пытается угадать устройство по IP или HWID.

1. Оператор доверенно регистрирует публичный ключ нового экземпляра ядра, создаёт UUID операции и запускает `begin-core-rotation`. Control переводит ноду в `quiescing`: новые подключения/lease запрещаются, старая identity остаётся зарегистрированной для получения подписанных drain-барьеров. Повтор с тем же UUID идемпотентен.
2. Для каждой действующей сессии выполняется deny+drain и ожидается подписанный core-fence именно для `session owner + generation + profile`. Пока нет подписанного подтверждения, слот остаётся **занят**, в том числе после потери связи.
3. На каждом rate resource отправляется `queue-rate-move` с `up=0`, `down=0`, затем требуется подписанный core barrier и его durable confirmation. Последний подписанный накопительный трафик для активного FUP должен быть получен **после** barrier.
4. Не раньше 45 секунд и только после отсутствия занятых сессий, нулевых rate grants, всех подтверждённых barrier и финального подписанного учёта вызывается `complete-core-rotation`. Один SQL commit закрывает прежние потоки, архивирует привязки, отзывает старую identity, регистрирует новую, переводит epoch grant и меняет pinned public key. `elx_node_inventory` и `elx_paid_profile_nodes` синхронизируются с новой incarnation/epoch.
5. Обновляется доверенный `ELX_POLICY_BINDING`, заново назначаются подписанные потоки (с новым boot/epoch), принимаются первые signed baselines, затем новые grants могут быть восстановлены через штатный журнал/барьеры. **Старые накопительные счётчики не переиспользуются**, а их история остаётся для аудита. Пока FUP/leases не готовы, продолжение пропуска трафика запрещено.

```bash
./elx-control begin-core-rotation \
  -rotation ROTATION_UUID -node NODE_UUID \
  -old OLD_BOOT_UUID -new NEW_BOOT_UUID \
  -new-public-key /etc/elx/next-core.pub

# Отключение всех сессий с подписанными core-fence и
# нулевые signed rate barriers — обязательные операции до следующей.
./elx-control complete-core-rotation -rotation ROTATION_UUID
```

**Что остаётся отдельной работой:** инфраструктурные действия запуска/остановки процессов ядра и финальная проверка физического нового core-instance на сервере. Этот код атомарно переключает *Control identity* лишь после проверенных fencing/usage, но не управляет установкой бинарника и не обходит недоступный VPS.

## Локальная проверка

В Windows 11 через WSL и Docker PostgreSQL настройте `ELX_TEST_POSTGRES_DSN` и выполните:

```bash
cd ElX-control
go test ./internal/elxcontrol/billing ./internal/elxcontrol/journal \
  ./internal/elxcontrol/management ./internal/elxcontrol/usagetransport -count=1
go test ./cmd/elx-control -count=1
```

Сценарии: неверная подпись/сумма, дубли provider payment, идемпотентная выдача и продление, ошибка ACK, отсутствие grants, stalled remote node, устаревший pinned key, смена эпох, запрет нового соединения при ротации, signed barrier и отказ от освобождения слота до подписанного fence.
