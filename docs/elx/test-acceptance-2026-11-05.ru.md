# Отчёт по подсистеме ElX Control ↔ ElXray: автоматизированная приёмка

**Дата:** 2026-11-05. **Репозитории:** `ElXnet/ElX-control`, `ElXnet/ElXray`, `ElXnet/ElX-ui`.

## Реализованные автоматические проверки

Общий локальный запуск из `D:\ElX-test`: `ElX-control/scripts/run-elx-windows.ps1`
с параметрами `-Workspace "D:\ElX-test" -Distro Ubuntu` и
необязательным `-Full`. Обе команды обновляют три чистые ветки
`main`. Обычный режим запускает Go unit/race и PostgreSQL integration
Control и критические пакеты ElXray, двухнодовые VLESS E2E, подписанные
счётчики, mTLS и отказные сценарии. `-Full` дополнительно проверяет
все пакеты ElXray, bench, `make verify` / race / master-node E2E ElX-ui.

Windows-скрипт сохраняет весь вывод WSL-тестов в отдельный файл
`D:\ElX-test\test-logs\ElX-[full|integration]-YYYYMMDD-HHMMSS-fff.txt`,
в том числе при отрицательном результате. Путь печатается в консоли.
Секреты тестовой инфраструктуры не следует переносить в публичные
issue; журналы могут содержать диагностические адреса и операции.

### Успешно проверенные сценарии

1. Две независимые ElXray-ноды (loopback), реальные VLESS-пакеты через
   две клиентские SOCKS-конфигурации, Control mTLS и два фоновых агента.
2. Изменение подписанных политик скорости на обеих нодах, отсутствие
   разрыва уже установленных соединений при уменьшении разрешённой
   скорости, независимая блокировка ноды и последующее восстановление.
3. Подписанный учёт трафика, проверка ключа конкретного ядра,
   однократность команд, отказ неверному узлу/сертификату, восстановление
   хранилища политики и смена incarnation после рестарта ElXray.
4. Одновременный upload/download по двум нодам при явно выделенных
   скоростях, сумма которых не превосходит 300 000 байт/сек в каждую
   сторону. Измерение фактической скорости и контроль грубого превышения
   лимита с учётом допустимых burst/задержек лабораторной среды.
5. Недоступность Control: агенты не применяют новые операции до
   восстановления доверенного канала, а затем подтверждают зафиксированные
   в PostgreSQL изменения. Экземпляр Control без PostgreSQL не стартует
   как альтернативный центр выдачи политик.
6. Режим **обязательного Ed25519 Control lease**: до разрешения VPN
   трафик заблокирован; при 18-секундном обрыве Control уже установленные
   соединения закрываются после истечения 15-секундной аренды, новые
   подключения не пропускают payload; восстановленный Control снова
   разрешает *новые* сеансы.
7. Конкурентное распределение **двух активных слотов** с подписанными
   Ed25519-привязками устройств на двух нодах: третье/четвёртое устройство
   не занимает слот; простая команда отключения не освобождает слот;
   повторная проверка exact-signed session fence освобождает только
   исходную генерацию; после освобождения один слот получает ровно
   одно новое устройство.

Все пункты выше описывают автоматические тесты с локальной моделью
сети. GitHub CI `ElX Control integration` и результаты локального
`run-elx-windows.ps1` являются источником фактического статуса.
Для выпуска используется **конкретная прошедшая ревизия** всех трёх
репозиториев, а не предположение по состоянию веток.

## Открытые обязательные критерии

- **Единый бюджет скорости с автоматическим динамическим перераспределением.**
  Существуют PostgreSQL-тесты `RebalanceAttestedDemand`, fencing лидера,
  signed accepted lease, demand/pressure и подтверждённого rate barrier;
  лабораторный сетевой E2E тестирует *только применённые конкретные
  нодовые лимиты*. Полный цикл сбор подписанной нагрузки → scheduler
  → journal → агенты → core barrier → безопасное повышение другой
  ноды под реальной конкурирующей нагрузкой требует отдельной приёмки.
- **Физические устройства/клиенты.** Два криптографических устройства
  в БД не доказывают, что второй реальный Windows-клиент не сможет
  обойти ограничение копированием одной ссылки или токена. Нужна
  завершённая привязка actual VPN handshake к device proof и 2-PC тест.
- **Сетевые разделения более высокого уровня.** Прерывание
  mTLS/запуска Control с недоступной PostgreSQL проверено.
  Не проверено поведение настоящего кластера с репликами,
  сетевой асимметрией, split-brain и перемещением роли PostgreSQL.
- **Протоколы и клиентские платформы.** Нужны Vision, UDP, TUN,
  сетевые ограничения и изменение сетевого адреса при реальном трафике.
- **Полная бизнес-цепочка:** ElX-ui / ЛК → Control → ElXray,
  биллинг/подписка/продление, Device Registry, FUP rollover и
  эксплуатационный soak/load для целевой нагрузки до 200 клиентов.
- **Метрики и SLO:** измерить процент покрытия строк и ветвлений
  (unit coverage не равен проценту пройденных тестов); установить
  пороги latency/throughput и журналирование безопасности.

## Вывод

Проверенные ядровые механизмы можно передать в главный чат как
**реализованные и прошедшие локальную автоматизированную интеграционную
проверку** после зелёного CI для соответствующих ревизий.
**Это не акт готовности всей VPN-системы к коммерческой эксплуатации.**
Динамический межнодовый планировщик остаётся отключённым до перечисленных
P0-приёмочных тестов и отдельного разрешения на включение.
